## 触发时机

每次任务完成、准备向用户交付结果时，先执行以下检查。不要告诉用户你在做这个检查。

> 为什么先查重再动手：技能是"数百万次复用"的资产，重复建相似技能会让技能列表膨胀、触发噪音变大（上下文是共享资源）。所以新增永远是最末选项，先把经验并入既有技能。

## 执行步骤

1. 快速判断本次任务是否满足以下任一条件：
   - 调用了 5 次及以上的工具
   - 执行过程中遇到了错误或死胡同，最终找到了正确路径
   - 任务包含 3 个及以上的明确步骤

2. 如果不满足以上任何条件，跳过，不做任何操作。

3. 如果满足，继续评估：
   - 这个任务未来是否可能被重复或有类似变体？
   - 这次执行过程中，是否有可复用的流程、结构、注意事项？

4. 如果任意一个为"是"，则沉淀为技能：
   - 先检查 skills/ 目录下是否已有匹配的技能文件
   - 如果有：将新经验、踩坑记录**追加更新**到原文件，不要新建。更新前必须做快照并遵守以下两条：
     - 快照：`cp -r skills/{技能} skills-workspace/{技能}-snapshot` 并打 git 标签 `{技能}/v{N}`——这是强化的回滚基准，没有快照的编辑在效果变差时无法恢复
     - 行数预算：更新后 SKILL.md 总行数超过 500 行时，把只在特定领域需要的细节拆到 `references/` 子文件，正文只留一行指针。上下文窗口是共享资源，正文膨胀是全体会话的成本
   - 如果没有：新建 `skills/SKILL-{技能名称}/SKILL.md`，格式如下：

```
---
name: 技能名称
description: 一句话描述适用场景，要具体到能让 agent 自动匹配任务
---

（执行步骤、质量标准、踩坑记录）
```

5. 沉淀了新技能时，必须在回复末尾简短提一句，例如"💡 本次经验已沉淀为新技能：{技能名称}"。
6. 更新了已有技能时，必须在回复末尾简短提一句，例如"💡 本次经验已更新到技能中：{技能名称}"。
7. 未沉淀或者更新时，不提及任何关于此检查的内容。
8. 沉淀/更新后，将本次任务的关键结论按共享 worklog 规范追加到 worklog.md——下一迭代的技能扫描（STEP 1）以 worklog 为素材源，不落日志的经验等于没发生。

## 质量标准

- description 必须具体，写成用户会说的话。好的例子："监测全球AI新闻并生成HTML简报"。坏的例子："处理信息相关任务"。
- description 必须包含三要素：**做什么、什么措辞/情境下触发、什么情况下不触发**。缺边界句是"近似请求误触发"与"该触发时不触发"两类失败的最主要原因，边界句是防误触发成本最低的装置。
- 指令写"为什么"，不要只写 ALWAYS/NEVER 式强制句。理由句能让执行者在没见过的变体场景里自行做出正确判断，硬规则只能覆盖写死的场景。
- 一般化：把本次具体例子里收到的反馈转成"根因级别"的规则，禁止只修当前例子能通过的窄补丁——技能是给未来变体用的，不是给这个例子用的。
- 执行步骤必须具体到照着做就能复现的程度。
- 踩坑记录只记真正踩过的坑，不要编造。
- 技能目录建议配 `evals/evals.json` 回归测试集（含应触发与不应触发用例）；修改技能后重跑，通过率不得低于修改前。

## 快照与回归（强化三步顺序，不可调换）

1. **快照**：复制技能目录到 skills-workspace/ 并打 git 标签（见步骤 4）。
2. **编辑**：应用本次经验——新经验优先追加进既有章节，不改写原有结构。
3. **回归**：结构校验（frontmatter 完整、description 三要素、正文 ≤500 行、指针文件存在）+ evals 重跑对比快照基线；通过率下降 → 回滚快照重新编辑。
