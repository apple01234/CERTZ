## 1. 확정한 범위 (사용자 선택)

| 카메라 | **방 전체가 한 화면에 들어오게** — 플레이어 추적 대신 방에 맞춤 |

던전 계열 role 정본은 `src/game/chapterStoryPlan.ts` 의 role 표에서 판별한다(새 표를 만들지 않았다):

실측 확인(`chapterPlace()` 를 실제 표로 순회):

| 값 | 측정 |
|---|---|
| 전체 스테이지 | **165** |
| framed room 적용 | **36** |

판정 예시 — `howlrstone1x1` cliff(야외, 미적용) · `howlrstone10x3` tunnel(적용) ·
`howlrstone11x1` throne(적용) · `howlrstone14x1` rift(적용).
같은 챕터 안에서도 `howlrstone11x3` court 는 미적용 — **챕터 단위가 아니라 스테이지(place) 단위**다.

## 2. 구현 — 순수 함수 모듈

`src/game/framedRoom.ts` 는 **Phaser 를 import 하지 않는다**(`creepZone.ts` 와 같은 방침).
→ 브라우저 없이 노드 테스트에서 그대로 검증된다. 이 방침이 이번 작업에서 유용했다:
결함 5개 중 **4개(2·3·4·5번)는 순수 함수로는 재현되지 않고 브라우저 실측으로만** 드러났고,
반대로 "계산 자체가 맞는가"는 노드 테스트가 즉시 잡아줬다. 두 계층을 나눠 둔 덕에
"계산은 맞는데 적용 이후가 틀렸다"는 판별이 가능했다(§7).

| export | 역할 |
|---|---|
| `FRAMED_ROLES` | 던전 계열 role 7종 집합 |
| `usesFramedRoom(place)` | role 판정. `place` 가 없으면 false |
| `roomBoundsFromLayout(open, cols, cellW, cellH, fbW, fbH)` | **개방 셀의 바운딩 박스**. 열린 셀이 없으면 스테이지 전체로 폴백 |
| `computeFramedView(roomW, roomH, screenW, screenH, pad, room)` | 줌·스크롤 계산. 줌 = `min(화면/방)` |
| `FRAME_PAD` | 프레이밍 여백 **96px** |

설계상 중요한 두 가지:

- **방 = 개방 셀의 바운딩 박스**이지 스테이지 사각형이 아니다. 스테이지 크기로 맞추면
  벽·빈 셀까지 포함돼 방이 화면을 넘치고 검정이 거의 안 보인다.
- **여백은 항상 둔다**(§4-5). 종전에는 "방이 화면보다 크면 여백 생략"이었는데
  던전 개방률이 45~80% 라 항상 커서 결과적으로 여백이 0이 됐다.

## 3. 카메라 적용 지점

`WorldScene` 쪽은 **계산하지 않고 적용만** 한다(`applyFramedCamera()`).

- `framedRoom` 플래그, `framedZoom`/`framedScrollX`/`framedScrollY` 보관
- `baseZoom` getter 가 framedRoom 일 때 `framedZoom` 을 반환 (줌 워치독과의 충돌 방지)
- `applyManualCameraFollow()` 진입부에서 framedRoom 이면 방 고정
- `applyCameraZoom()` 분기, 보스 인트로 팬 생략
- `cam.setZoom(1)` 로 되돌린 뒤 뷰포트를 잰다(§4-2)
- `cam.useBounds = false` — 켜져 있으면 Phaser 가 scroll 을 bounds 안으로 클램프해 여백이 사라진다
  (실측: 켜져 있으면 1.5초 뒤 scroll 이 `56/-84` → `423/228` 로 밀려 여백 소멸)

## 4. 실측으로 잡은 결함 5개

이 작업은 "코드를 고치면 바로 되는" 종류가 아니었다. 5개를 차례로 밟았다.
**전부 스크린샷 또는 콘솔 수치로 확인한 것이며, 추정으로 적은 항목은 없다.**

| # | 증상 (실측) | 원인 | 수정 |
|---|---|---|---|
| 1 | 프레이밍이 전혀 안 걸림 (`framed:false`) | 프로브가 `howlrstone14` 같은 **없는 키**로 이동 시도. 실제 스테이지 키 형식은 `howlrstone14x1`(`parseStage` 정규식) | 측정 스크립트의 키 수정. **코드 결함 아님** |
| 2 | 줌이 **2.025** 로 튀어 방이 잘림 | `applyCameraZoom` 이 resize 시 `setZoom` 을 먼저 호출 → 그 뒤 `cam.width` 로 계산하면 화면 크기를 잘못 잼 | 계산 전 `setZoom(1)` 로 되돌려 실제 뷰포트 픽셀을 잰다 |
| 3 | 줌이 계속 **0.745** 로 복귀 (의도 **0.552**) | 매 프레임 도는 **줌 워치독**이 `baseZoom`(= viewZoom)으로 되돌림 | `baseZoom` getter 가 framedRoom 일 때 `framedZoom` 반환 |
| 4 | 좌우 검정 **0px** (방이 화면을 꽉 채움) | 지면 렌더러가 `role === "ground"` 일 때 **모든 셀**에 바닥을 침 | framedRoom 이면 **열린 셀에만** 칠한다 |
| 5 | 상하 검정만 보이고 좌우는 없음 | `pad` 를 "방이 화면보다 크면 생략"했는데 던전은 개방률 45~80% 라 항상 큼 | `pad` 를 **항상** 적용 |

### 결함 1은 코드가 아니라 측정 도구의 버그였다

`howlrstone14` 로 이동을 시도하면 스테이지 전환이 일어나지 않으므로 `framedRoom` 이 false 로 남는다.
즉 **"기능이 안 걸린다"는 측정 결과 자체가 거짓**이었다.
`parseStage()` 의 정규식은 `^(howlrstone(?:[1-9]|1[0-5]))x([1-9]|10)$` 이다(`src/game/stages.ts`).
`howlrstone14` 는 이 정규식에 걸리지 않아 `{ ch: "village", sub: 0 }` 로 **조용히 폴백**하고,
`chapterPlace("village", 0)` → `undefined` → `usesFramedRoom(undefined)` → **false** 가 된다.
반면 실제 키 `howlrstone14x1` 은 `{ ch: "howlrstone14", sub: 1 }` → `rift` → 적용.

즉 **스테이지 전환이 일어나지 않았는데 코드는 아무 오류도 내지 않았다.**
`parseStage` 가 실패 시 예외 대신 village 로 폴백하는 설계라 측정 스크립트가 침묵 속에 틀린 표본을 쟀다.

→ **기능이 안 걸린 것처럼 보이면, 먼저 그 스테이지에 실제로 들어갔는지를 의심해야 한다.**
프로브는 이동 후 현재 스테이지 키를 함께 찍어 남겨야 한다.

### 결함 3·4는 서로 다른 층이 같은 화면을 덮고 있었다

카메라(3)와 렌더(4)가 **동시에** 잘못돼 있었다. 카메라만 고치면 화면이 안 바뀌고,
렌더만 고치면 여백이 안 생긴다. 아래 §5 의 교훈이 여기서 나왔다.

## 5. 교훈 — "고쳤는데 화면이 그대로"일 때

이번 기능의 카메라 값에는 **독립적인 기록자(writer)가 5개** 있었다:

1. `applyCameraZoom()` — resize 시 `setZoom`
2. `followOffset` / `startFollow` — 플레이어 추적
3. **줌 워치독** — 매 프레임 `baseZoom` 으로 복귀
4. **보스 인트로 팬** — 진입 시 카메라 이동
5. **camera bounds 클램프** — `useBounds` 가 scroll 을 밀어냄

하나를 고쳐도 다른 넷이 덮어쓰면 화면은 그대로다. 그래서 **어느 레이어가 덮고 있는지
층별로 지워가며** 확인해야 한다. 실제로 `useBounds` 는 `create()` 에서 꺼 뒀는데도
`setBounds(…, true)` 가 다시 켜서 살아났다 — 이건 코드를 읽어서는 안 보이고 실측으로만 보였다.

## 7. 미해결 / 확인 필요 ⚠️

**좌측 여백이 0px 로 남는 결함이 있다. 이 문서 작성 시점에 다른 작업자가 수정 중이며,
이 문서는 그것을 "고쳐졌다"고 주장하지 않는다.**

### 관측된 증상

| 스테이지 (role) | 측정 원본 | 좌 여백 | 우 여백 | 판정 |
|---|---|---|---|---|
| `howlrstone10x3` (tunnel) | `.shots/par-howlrstone10x3.png` | **83px** | **81px** | **정상** |
| `howlrstone11x1` (throne) | `.shots/par-howlrstone11x1.png` | **0px** | **111px** | 비대칭 — 좌측 잘림 |
| `howlrstone11x1` (throne) | `.shots/final-howlrstone11x1.png` | **0px** | **85px** | 비대칭 — 좌측 잘림 |
| `howlrstone14x1` (rift) | `.shots/par-howlrstone14x1.png` | **0px** | **104px** | 비대칭 — 좌측 잘림 |

(측정: 1280×800 원본에서 HUD 상단과 대사창 영역을 제외하고 열 단위 비검정 픽셀 수로 판정.
같은 스테이지 `howlrstone11x1` 을 두 번 재서 **우측 여백만 111 → 85 로 달라졌다** —
좌측 0 은 고정, 우측은 가변. 원인은 미확정이나 "좌측이 잘린다"는 사실은 재현성이 있다.)

### 측정된 두 개의 서로 다른 값 (핵심 단서)

`applyFramedCamera()` 를 **수동 호출**하면 계산값이 옳고 그 값이 유지된다:

- zoom **0.5521**, scrollX **56**, scrollY **−84**

그런데 **정상 플레이 중** 실제 카메라는:

- zoom **0.7454**, scrollX **931**, scrollY **244**

→ **계산 경로는 의도한 값을 만들어내고 있었고, 문제는 그 뒤였다.**
같은 함수가 같은 스테이지에서 두 값을 내는 게 아니라, **적용 이후 다른 경로가 값을 밀어낸다**는 뜻이다.
§5 의 기록자 목록 중 하나 이상이 framedRoom 에서도 살아 있다.
(어느 것인지는 특정하지 못했다 — §7 "확인하지 않은 것".)

### 관측 당시 조건

- `camCinema` **true**, `dialoguing` **true** — 입장 튜토리얼 대사가 떠 있는 상태였다.
  대사가 카메라를 잡아두는 경로(`sceneCinematic`)와의 상호작용이 유력하나 **미확정**이다.
- `howlrstone10x3` 만 정상이라는 사실이 중요하다. 조건 차이(대사 유무·컷씬 길이)를
  비교하면 원인을 좁힐 수 있다. **이 비교는 아직 하지 않았다.**

### 이 문서에서 확인하지 않은 것 (추정 금지)

- 위 결함의 **원인 확정** — 기록자 중 무엇이 범인인지 특정하지 못했다.
- 수정 후 재측정 — 수정이 진행 중이라 **수치가 곧 낡는다**.
- 전 36개 framed 스테이지 순회 측정 — 표본은 3개 스테이지다.

- **방 자체가 원래 크다.** 던전 레이아웃이 스테이지의 45~80% 를 개방하므로
  방 바운딩 박스가 **2100×1024** 같은 값이 나온다(실측 `howlrstone11x1`).
  여백 96px 로 맞추면 줌이 약 **0.55** — 캐릭터가 작아 보인다.
  참조 이미지(작은 방 하나)와 같은 느낌을 원하면 **던전 개방률 자체를 낮추는 별도 작업**이 필요하다.
  이번 범위는 "던전을 검정 위에 띄우는 렌더/카메라"까지다.
- **`tsc --noEmit` 재실행 안 함.** 작성 시점에 피수정 파일이 편집 중이어서,
  지금 돌린 결과는 움직이는 표적을 재는 것이 된다. 통합 후 재검증이 필요하다.
- 야외 스테이지는 이 스타일을 쓰지 않는다(사용자 선택). 이는 테스트가 실제 챕터 표를
  순회해 던전/야외 판정이 배타적인지 고정한다.
