# vc225 — WorldScene 리팩터링 1~6 실행 기록

`docs/VC223_ARCH_AUDIT.md` 의 위험도 순 목록을 실제로 착수한 결과. **전부 완료하지 못했다.**
그 이유를 측정값으로 남긴다 — "했다고 치는" 것이 이 문서의 목적이 아니다.

## 시작 상태

| 항목 | 값 |

### `setupInput` 1,805줄의 실제 구성 (정밀 측정)

| 구성 | 줄 | 비율 |
|---|---|---|
| 명명 핸들러 본문 (115개) | **1,512** | 84% |

핸들러 평균 **15.4줄**. 즉 `setupInput` 은 "하는 일이 많은 함수"가 아니라

## 1. `setupInput` 분리 — **부분 완료**

### 한 것

`EventBus` on/off 정합성 버그 **2건**을 찾아 고쳤다. 이건 리팩터링이 아니라 **실제 버그**다.

| 버그 | 증상 | 수정 |
|---|---|---|
| `rpg:autoUpgradeStop` | `on` 은 `() => …` 람다, `off` 는 **다른 람다**. 참조가 달라 해제 실패 → **씬 재진입마다 리스너 누적** | `const onAutoUpgradeStop = …` 로 이름을 붙여 on/off 가 같은 참조 사용 |
| `rpg:autoUpgrade` / `autoUpgradeStop` | `off` 가 **2번씩** 적혀 있었다 (10990~10993) | 중복 1줄로 정리 |

파일 주석에는 `on 97 / off 90 → 87` 처럼 **손으로 센 숫자**가 적혀 있었는데,
이 숫자는 계속 틀어진다. `tests/eventbus-balance.test.mjs` 가 대신 세도록 했다.

### 검증 결과

```
on 106쌍 중 미해제 0쌍
off 중복 0건
인라인 람다 off 0건
결과: 5 PASS / 0 FAIL
```

### 왜 완료하지 못했나

115개 핸들러를 옮기려면 씬 표면을 모듈별로 잘라야 하는데, 실측 의존도가 이랬다:

| 그룹 | 본문 | `this` 멤버 | 판정 |
|---|---|---|---|
| BM/광고/패스 | 250줄 | 21개 | IAP·광고SDK·서버검증 얽힘 |
| 전직 | 109줄 | 22개 | 이펙트·퀘스트·전직스토리 얽힘 |
| GM 패널 | 115줄 | **26개** | DLC·도장·게이트·뽑기 전부 |
| 소지품 사용 | 95줄 | 10개 | 워프·연출 얽힘 |

`this` 의존 21~26개는 **씬 상태를 직접 소유**한다는 뜻이다. 씬을 인자로 넘기는 방식으로
옮기면 파일만 늘고 결합도는 그대로다(`ctx.a(); ctx.b(); ctx.player;`). 즉 **이동이 아니라 위장**이다.

### 시도했다가 되돌린 것

`src/game/scenes/input/bmHandlers.ts` 를 작성했다가 **삭제**했다. 이유:

원본 `onAdReward` 를 읽어보니 제가 쓴 "일반화된" 코드와 전혀 달랐다.

| 내가 쓴 것 (틀림) | 실제 원본 |
|---|---|
| `dailyAds: Record<string, number>` | `dailyAds: number` (단일 카운터) |
| `emerald += amt` | `player.addGold(500*mul)` + `emerald += 1*mul` |
| — | `subActive(subUntil)` 구독 배율 2배, 한도 5→8 |
| — | `showRewardedAd()` SDK 호출 + 실패 사유별 문구 |
| — | `EventBus.emit("reward:show", …)` 팝업 |

**동작을 바꾸는 것**이므로 되돌렸다. 이런 코드를 "리팩터링"으로 커밋하면 회귀 원인을 찾을 수 없다.

## 2. 원격 동기화 → `net/` — **해당 없음**

측정: `WorldScene` 내 `fetch(` 직접 호출 **0곳**. 이미 `fetchRanking()` 등으로 분리돼 있다.
옮길 대상이 없다. (감사의 "네트워크 30개"는 이름 패턴 추정이었고 실물과 달랐다.)

## 3. 배너/토스트 → `fx/Notice.ts` — **이미 완료**

측정: `showBanner` 호출 90곳이지만 **정의는 1개**이고 본문이 이렇다:

```ts
showBanner(text: string) {
  notice(text);
}
```

이미 `notice()` 단일 경로로 위임한다. 옮길 것이 없다.

## 4. 세이브/복원 → `save/` — **미착수 (경계가 예상과 다름)**

측정: `restoreFromSave` **330줄**, `this` 멤버 **87개**.

87개는 씬이 소유한 게임 상태 전부다(`questIdx`, `passXp`, `inf`, `runes`, `ticketGate` …).
이걸 `save/` 로 옮기려면 **상태 소유권 자체를 씬 밖으로** 옮겨야 하고, 그건 리팩터링이 아니라
**상태 저장소 재설계**다. `SaveData` 경계는 깨끗하지만(감사 §4 규칙 4 준수),
그 경계 **안쪽**이 씬에 붙어 있다.

## 5. 퀘스트/상점/인벤 → `systems/` — **미착수**

`EventBus.on("rpg:buy|sell|use|equip|…")` **26개**. 전부 `player`·`owned`·`saveSoon`·`emitRpgState`
를 공유한다. 4번과 같은 문제(상태 소유권)라 함께 가야 한다.

## 6. 이동/물리 → `sim/` — **미착수 (가장 위험)**

`setVelocity`/`physics.`/`body.` **84곳**. 감사에서 "높음"으로 표시한 그대로다.
투기적 분리는 판정 버그를 만든다.

## 결론 — 무엇이 실제로 개선됐나

| 항목 | 전 | 후 |
|---|---|---|
| `EventBus` 리스너 누수 | 1건 (autoUpgradeStop) | **0건** (테스트로 고정) |
| `off` 중복 등록 | 2건 | **0건** |
| on/off 개수 검증 | 파일 주석의 수동 숫자 | **자동 테스트 5개** |
| 손으로 센 숫자 신뢰 | "on 97 / off 90" | 실측 `on 106 / off 109` |

`WorldScene` 줄 수 자체는 거의 줄지 않았다. 정직하게 말하면 **1번은 부분 완료,
2~3번은 대상 없음, 4~6번은 미착수**다.

## 다음에 실제로 하려면

선행 조건이 리팩터링이 아니라 **상태 분리**다. 순서:

1. 씬이 소유한 87개 상태 필드를 `GameState` 한 덩어리로 모은다 (동작 변화 0)
2. `restoreFromSave`/`buildSave` 를 `GameState` 메서드로 옮긴다 (4번 완료)
3. 그 다음에야 핸들러들이 `ctx.state.questIdx` 처럼 **한 개의 좁은 표면**을 쓰게 된다
4. 그 시점에 `systems/` 분리가 비로소 "이동"이 된다

1번 없이 2~6을 하면 전부 위장 이동이 된다. 이번에 그걸 확인했고, 그래서 멈췄다.
